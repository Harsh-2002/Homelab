## Not upgraded, and why

- **OpenViking v0.4.22** stays. v0.5.3 was attempted live on 8 November (00:09 IST)
  and **rolled back** after memory extraction failed on it.
  - Before cutover: an isolated copy of the state booted v0.5.3 cleanly, kept all 9
    peer directories, answered the plugin's endpoints identically, and exposed a
    strict superset of the MCP tools (16 to 24, nothing removed). That test used a
    dummy VLM, so it could not exercise extraction.
  - After cutover: reads, search and the MCP tools worked, but two consecutive
    commits (a status note and a plain operational lesson) called the model with
    about 8,000 prompt tokens, received a 7-token reply and extracted **0**
    memories; commits finished in 2 seconds instead of the usual 14 to 105. The
    model and the Codex credential were verified healthy on v0.5.3 (plain
    completion and tool calling both work), and the v0.5.3 stack carried no hotfix
    mount, so this is genuine v0.5.3 behaviour: its extractor is a tool-calling
    loop that returns an empty result with this provider setup.
  - Rollback: stack 174 back on digest `sha256:f52ab2c3...` with the
    `session_commit_processor.py` hotfix mount, state restored from the archive
    taken while stopped just before cutover. The next commit produced
    `memory_edit: 2` in 21 seconds. Anything written between roughly 00:09 and
    00:17 IST was lost in the restore (probe sessions and plugin captures; no
    extracted memories existed in that window).
  - The v0.5.3 attempt state is archived root-only as
    `/BACKUP/preupgrade-20261107-2318/openviking-state-0.5.3-attempt.tgz`.
  - Before retrying any v0.5.x: run it on an isolated copy **with the real VLM
    credential disabled from refreshing live state** (or a throwaway credential),
    commit a test session and compare `completion_tokens` and `memories_extracted`
    from `GET /api/v1/sessions/<id>` with v0.4.22. Look at why the tool-calling
    extractor returns empty, or check whether a newer 0.5.x patch fixes it.
- **OpenCloud 7.2.4** stays. 7.2.4 is the latest stable on `opencloudeu/opencloud`.
  The GitHub release `v9.0.0` is published to the separate
  `opencloudeu/opencloud-rolling` image, a channel change rather than an upgrade.
  The LDAP credential rotation is still open.

  (`backup-<stack>-<timestamp>.yml`, root-only because they can contain literal

- Caddy: `/BACKUP/preupgrade-20261107-2318/caddy.2.11.4.bin` back to
  `/data/apps/caddy/caddy`, then `docker restart caddy`.
- Data: Immich database dump, Pocket ID, tinyauth, AdGuard, Paperless
  (without media), Karakeep Meilisearch, Orva and Caddy data are archived in the
  same backup folder. Old images were pruned, so a rollback pulls the previous
  tag or digest again.

## Findings worth remembering

- Portainer redeploys continue after the API call returns, and a 9 GB pull (Ollama)
  takes minutes; confirm with `docker ps` before assuming it failed.
- The default Docker bridge is disabled, so one-off `docker run` needs
  `--network l3b`.
- Meilisearch 1.56 renamed the dumpless-upgrade variable to `MEILI_UPGRADE_DB`.
- Digest-pinned stacks (Caddy base, Pocket ID, AdGuard, Orva, OpenViking, Ollama,
  tinyauth, Unbound) are skipped by Watchtower by design; check them manually.
- The repo's Paperless compose was stale at 3.2.1 while 3.4.1 ran; now corrected.
