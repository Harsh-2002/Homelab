# Cluster interruption and recovery — 31 October 2026

All times below are IST. The owner noticed the interruption around 08:00 on
31 October and used the power buttons only after 10:00. Earlier power-key events
must therefore be treated as unsolicited. Earlier successful finite reboot
tests did not establish the cause or sustained reliability.

## Evidence and limits

- **px20 first disappeared at 17:40 on 30 October.** Its journal ends abruptly
  at 17:40:02. px10 saw the Corosync link fail at17:40:08 and node loss at17:40:13.
  Historical monitoring independently changed to down from17:41. No sleep entry,
  orderly shutdown, OOM, panic, NIC watchdog/hardware-unit hang, storage reset or
  thermal trip was recorded in that boot. Last reported RAM was about94.7%, CPU
  temperature63°C, with no sampled memory-pressure stalls in the examined window.
  These measurements do not identify or exclude an underlying hardware fault.
  No pstore dump was available. **The original abrupt-loss cause is unresolved.**
- **px10 could not accommodate Docker failover.** HA tried starting VM204 after
  fencing px20. At17:43:18 the px10 kernel OOM-killed its QEMU process in
  `/qemu.slice/204.scope`; HA entered error at17:43:30. VM204 requires16GiB and
  shares the32GiB fallback host with other workloads. Replication and HA affinity
  alone do not provide enough spare RAM. No N+1 availability guarantee is valid
  for this placement. No memory reductions, extra swap or fencing changes were
  made during recovery.
- **px30 began orderly shutdown sequences following power-key events** at04:39:30,
  04:49:10,08:07:32 and08:38:23 on31 October. Logind explicitly logged a short
  power-key press followed by powering off. The owner did not press it at those
  times. These logs do not identify which physical/firmware/input source emitted
  the events. A faulty physical button or a BIOS/ACPI issue is a hypothesis,
  not a confirmed diagnosis. No permanent power-key suppression was applied.
  Reinspection of boot tails: the04:39 log ends while waiting for VM203 to stop;
  the04:49,08:07 and08:38 sequences reach poweroff.target and systemd-shutdown,
  then journald stops (04:53:13,08:11:19,08:38:35 respectively). These establish
  software shutdown progression, not successful physical power removal. The owner
  observed front-panel lights on, no disk activity and active switch links. A
  final firmware power-off stall remains possible; it is not proven. NIC link
  lights can also remain powered for Wake-on-LAN after host shutdown. Do not
  equate a shutdown request or poweroff.target with confirmed hardware-off.
- With px20 already absent, px30 loss left px10 without quorum. Its HA watchdog
  expired at04:41:14 and08:12:17, followed by new boots. Those are fencing safety
  responses in the observed cascade. They are not evidence of hibernation.
- No actual suspend/hibernate entry was found in the examined journals.
  All three hosts reported logind `IdleAction=ignore`. Boot messages mentioning
  hibernation memory regions and registered sleep buttons do not mean sleep
  occurred. Link lights alone cannot distinguish a running OS from a hung host.

## Restoration

Restored all13 guests to the normal placement documented in
[RETURN-TO-SERVICE.md](RETURN-TO-SERVICE.md). Cleared VM204's HA error with the
supported disabled state, relocated it to px20, then requested started. Docker
containers recovered with existing disks/configuration.

VM106's automated return failed repeatedly because the target had an orphaned
generated cloud-init volume. Temporarily set only VM106 ignored, verified the
target did not own its config and no local config referenced that generated
volume, then removed only that target cloud-init volume. The source cloud-init
and replicated data disk remained intact. Native offline migration completed;
restored HA state started. Both VM106 and VM204 run on px20 again. All ten native
replication jobs are enabled with zero failures and fresh successful syncs.

Supabase primary1 and standby3 were healthy; stale standby2 required WAL already
removed upstream. Verified primary identity, an active streaming survivor and
PVC ownership before retiring only standby2 with the matching official CNPG1.30.1
destroy command. The temporary CLI archive was SHA256-verified and removed.
The operator cloned a new standby2. SQL subsequently verified both2 and3 as
streaming/quorum, including live WAL receivers. Only after those checks and
confirming no current PVC reference was the obsolete Released/Retain PV switched
to Delete for native CSI cleanup. No primary reset or forced promotion.

Home Assistant was waiting to retry Frigate after Docker downtime. Reloaded only
the existing Frigate integration. Camera recording state, authenticated snapshot,
media browser and actual HLS segment retrieval then passed. No light/AC commands
were sent. The Samsung AC was previously confirmed switched off at mains.

## Follow-up required

Recovery is not a root-cause fix. Identify px20's abrupt failure and px30's
unsolicited power-key source, and establish a measured failover memory budget
before claiming HA. px20 has little RAM headroom after normal workloads return.
Do not disable quorum/watchdogs to conceal the cascade. The configured SMTP
notifications also showed unauthenticated sender rejection during failover;
alert delivery needs a separate verified repair, without sending unapproved mail.
