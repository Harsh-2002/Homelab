# Supabase functional and HA audit, 2026-10-18 UTC

Scope: the single Kubernetes Supabase deployment. VM108 no longer exists.
No node drain/shutdown, force-delete, PVC deletion or durability relaxation was
performed. Use the current README for access, credentials and backup limits.

## MCP transport failure: reproduced and route-scoped mitigation verified

Before repair, 6/60 external requests failed HTTP502. Matching Kong request IDs
logged `upstream prematurely closed connection while reading response header`.
Direct calls to the Studio service and both individual pod IPs also failed with
`UND_ERR_SOCKET`, ruling out Caddy/Kong as the initiating layer. Direct loopback
A/B: reused connections failed3/60; Connection:close passed60/60 and120/120.

The deployed Studio uses MCP SDK1.29.0's Node/Hono HTTP adapter. The evidence
isolates reused HTTP/1.1 connections on this endpoint; the precise SDK/framework
code-level cause is not proven. Do not claim a patched upstream library.

The existing Kong post-function plugin now sets `ngx.var.upstream_connection =
'close'` only on service `mcp`. Auth, REST, Storage, Realtime and client keepalive
remain unchanged. Source gate10.1.1.3, Caddy Bearer authentication and denied
`/api/mcp` remain enforced. No new service, proxy or custom image was introduced.

Stable-window post-change runs passed150/150,150/150 and300/300 with concurrency
up to4. The final300-call batch took6.97s, maximum latency0.393s. Native MCP auth,
11-tool discovery, actual SQL reads and temporary writes also passed. A separate
300-call batch during the DB switchover returned200 successful discovery/setup
calls and100 SQL tool errors, but zero transport502s; this is expected database
unavailability, **not** a successful HA SQL run. Do not hide it in success totals.

## PostgreSQL HA

Preflight: three healthy instances on separate nodes; two streaming quorum
standbys with millisecond lag; synchronous_commit=on, ANY1 standby, healthy
Longhorn volumes. Enabled supported CNPG1.30 `failoverQuorum:true` to require
quorum evidence before automatic promotion. This is not an independent backup.

Planned switchover db2 -> db1 retained the acknowledged UUID test row, then the
test removed its own table. Recovery119.69s;25 SQL probes failed; measured failed
probe span111.44s. **It required intervention:** after the old primary's successful
checkpoint/fast-shutdown request, its logical WAL sender serving the Realtime pod
at10.244.2.140 remained in START_REPLICATION and blocked shutdown. Gracefully
replacing that exact Realtime pod released the connection; shutdown and promotion
then completed. No PostgreSQL kill, force promotion or volume edit was used.

This is an OPEN planned-maintenance HA blocker, not a clean automatic HA pass.
CNPG's switchoverDelay remains its3600s default. Do not silently shorten it:
upstream documents that an immediate shutdown fallback trades RPO against RTO.
No additional disruption drill should run until the blocker/procedure is reviewed.
Full node loss, partitions, fencing and replacement-cluster DR remain untested.

Realtime v2.134.10 deliberately creates TEMPORARY logical slots without failover.
Both observed slots are temporary and non-failover. They are recreated on
reconnection; converting them is not a supported configuration fix. The CNPG
synchronizeLogicalDecoding option does not make these temporary slots durable.
Post-failover Realtime subscription, row update delivery and RLS tests passed.
This does not establish lossless replay of every transient event across failover.

## Query statistics: actual recurrence mechanism found by HA testing

After promotion pg_stat_statements disappeared again. The initial image seed and
the repair had created it, but CNPG's managed-extension logic removes its SQL
objects unless a pg_stat_statements.* parameter enables management. Merely listing
the shared preload library was insufficient. This explains recurrence during
reconciliation/promotion; it supersedes the earlier unproven omission explanation.

The Cluster now declares pg_stat_statements.track:top. CNPG recreated the extension
in public; migration v5 moves this relocatable extension into extensions without
dropping/recreating it. Tests accept either supported search-path location rather
than treating schema placement as a missing extension. The static init-contract
guard requires the managed parameter. Existing completed Job templates were not
mutated: the new versioned Job is supabase-observability-init-v5.

## Storage recovery

The first Storage restart overlapped the DB test and measured154.3s with62 REST
probe errors. This result is confounded and is NOT the isolated Storage RTO.
The helper now serializes drills with a process lock and requires all deployments
ready before starting. A separate stable-database repeat recovered in34.4s;
19 Storage probes failed, measured failure span29.38s, zero REST probe errors.
The test file retained SHA256
58dddc071afaad7eeef96dd57d0a835d0ac05519047cf13510a6a040ece6561a.

Storage restarted on the same node. This proves process recovery/persistence,
not cross-node block-volume reattachment or zero-downtime Storage. The selected
single-replica RWO architecture necessarily interrupts file access on recovery.

## Application and Studio acceptance

After recovery: protected HTTPS/SSO, API auth, ES256 login/refresh, REST CRUD and
two-user RLS, private Storage and signed-link expiry, JWT-enforced Edge Functions,
Realtime events/RLS and retained database/file fixtures passed. Generated users,
table, bucket/file, trigger and audit fixtures were removed by their own helpers.
Expanded platform tests verify required extensions/callable statistics on every
instance, Studio metrics/role/cache queries, catalogs, advisor prerequisites,
real webhook POST and transactional extension enable/disable.

Browser checks: Query Performance, extension listing, Performance/Security
Advisors and database functions load without observed missing-relation errors.
Advisor run-lints endpoint returned200. Two performance warnings belonged to the
disposable acceptance table and disappeared after cleanup. The initial two
extension-in-public warnings were pg_stat_statements and pg_cron. The former is
relocatable and migration v5 addresses it. pg_cron is non-relocatable in this
image, with its actual objects in cron; anon lacks USAGE on cron. Preserve this
remaining warning as a documented packaging exception, not an all-green claim.
No claim that every optional/hosted-only screen/action has been tested.

## Reproduce safely

- `python3 infrastructure/supabase/audit-mcp.py --calls 150 --workers 3`
- `python3 infrastructure/supabase/validate-platform-init.py`
- Venv Python: `infrastructure/supabase/validate.py --keep` before persistence
  checks; omit --keep afterward to verify and remove the owned fixtures.
- Venv Python: `infrastructure/supabase/validate-ha.py storage-restart --execute`
  only after the fixture setup and a maintenance decision.
- Switchover helper refuses active logical consumers by default. Do not use
  --allow-active-logical-slots without acknowledging the known blocker and an
  explicit controlled maintenance plan. Do not run disruption tests concurrently.
