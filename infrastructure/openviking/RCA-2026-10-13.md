# OpenViking SessionCommit queue incident

## Evidence and impact

On 2026-10-13 Studio showed Task Queue unhealthy while five other components were healthy. OpenViking v0.4.22 and Ollama containers were healthy, Ollama was idle, and the data disk had about 146 GiB free. The SessionCommit queue contained four stranded processing deliveries and roughly 145 unfinished archives from Codex session `cx-01a10fb7-a379-7202-b727-f56e0ed11863`. Exact pending counts changed as further captures arrived. Its requeue counter exceeded 1.45 million; processed counts include requeued deliveries and are not successful extraction counts.

The four stranded deliveries corresponded to these worker exceptions (UTC):

| Archive | Worker error time | Error |
| --- | --- | --- |
| 110 | 2026-10-09 23:15:46 | JSON expecting value at character 0 |
| 135 | 2026-10-12 06:03:34 | Unterminated JSON string at character 239 |
| 137 | 2026-10-12 06:03:34 | Unterminated JSON string at character 280 |
| 238 | 2026-10-13 08:35:48 | Unterminated JSON string at character 251 |

Read-only SQLite inspection confirmed these deliveries still in `processing`, while the task API reported no running tenant tasks. All decoded persistent queue payloads, affected archive JSONL records, and inspected metadata/marker files were valid at inspection. Archives 107–109 had completed, ruling out the earlier oversized-prompt failures as the immediate predecessor blocker for archive 110.

## Cause and confidence

Confirmed: an exception escaping a concurrent queue handler skips acknowledgement, leaving the delivery in processing for startup recovery. Archive-order dependencies then make later commits requeue until the predecessor becomes terminal. QueueObserver reports unhealthy when a queue has recorded errors and unfinished work.

Strongly supported trigger, but not a captured failing-read traceback: the producer enqueues before finishing its locked root-session rewrite, while SessionCommitProcessor reads `session.load()` before the Phase-1 readiness/lock barrier. Reading a JSON file during its rewrite explains an empty or unterminated document followed by valid files on later inspection. The deployed logger omitted the exception traceback, so the exact read that failed was not proven. The narrow guard fixes this identifiable race without assuming durable corruption.

## Applied change and cutover

- Retained the official v0.4.22 image, local all-minilm embeddings, gpt-6-luna VLM, current keys and persisted volumes.
- Installed a reproducible, read-only processor-module bind through Portainer API, stack 151, endpoint 2.
- Protected `session.load()` with the same exact session PathLock as the producer; released the lock before Phase 2, including on exceptions.
- Regression tests cover waiting for a writer, releasing after read failure without hiding the exception, and running Phase 2 outside the root lock. All three passed before and after deployment.
- Finalized and verified the single state backup while gracefully stopped; did not directly update queue SQLite, clear queues, delete archive data, or mark pending tasks successful.
- Portainer cutover to healthy API took 23.39 seconds. Ollama retained its original start time.

## Validation and remaining recovery

- The deployed process loads the read guard and both containers are healthy.
- Unauthenticated task API requests still return HTTP 401.
- Existing memory search and exact resource reads work through MCP.
- 444 archived message files and 364 resource files matched the backup byte-for-byte.
- The vector count remained 609 at the preservation check; subsequent legitimate extraction may update it.
- Native startup recovery reclaimed the stranded work. Archive 111 completed memory extraction with one memory edit and zero skipped operations; later archives began progressing.
- Archive 110 reached extraction but its model stream closed prematurely (`incomplete chunked read`); its raw archive remains intact and it is explicitly failed, not silently discarded. This upstream transport failure is separate from the repaired queue read race.
- The historical backlog was still draining at initial validation. A green health indicator is not proof that all queued or historically failed archives extracted successfully.

Do not claim all extracted memory is recovered until the backlog and failed tasks are individually verified. Do not blindly replay older failed archives out of order over newer extracted facts. A controlled replay plan must preserve raw inputs, completed steps and current memory state.

The override is version-specific. Rebase or remove it after validating an upstream fix; rollback should remove the bind, not restore old data over new writes. General worker-exception retry policy and provider request-size/stream handling were not redesigned in this scoped repair.
