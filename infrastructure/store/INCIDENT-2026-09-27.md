# 2026-09-27 Store outage and DNS failover RCA

## Impact

After host reboots, CT 109 (`store`) ran on px20 while its USB SSDs remained on px10. Its host bind paths existed but were not mounted data volumes. The `AV`, backup, and `ISO` SMB shares were unavailable. `ctr` could not mount `AV`, so Motrix stopped and Homepage could not load its favicon. Proxmox Pocket ID sign-in was intermittent while DNS was unhealthy.

## Root causes

1. The three host mount units had `After=local-fs.target`. Systemd automatically orders local mounts before `local-fs.target`, creating a boot ordering cycle; systemd dropped the mount jobs. The px10 journal explicitly showed `Found ordering cycle on mnt-external-AV.mount/start` and `Job ... deleted to break ordering cycle`, with the same pattern for the backup and ISO mounts. Unit files now omit that contradictory ordering, allow a 60-second device wait, and are staged on both HA nodes. A future host reboot has not yet been used to validate this live; check the mount units after the next planned reboot.
2. CT 109's `mp0`/`mp1`/`mp2` are local bind mounts, not shared storage. Proxmox correctly rejected a GUI/HA migration with `cannot migrate local bind mount point 'mp0'`. A directory's existence on both hosts does not make the USB filesystem shared. Setting `shared=1` would only suppress Proxmox's check and could start the CT against empty directories; it is intentionally not used.
3. Unbound's persistent files lacked `port: 5335`; a restart put it on port 53 while AdGuard queried loopback port 5335. The tracked `unbound-recursive.conf` now declares the loopback listener and cache settings. `unbound-checkconf`, restart, port-5335 recursion, and AdGuard port-53 queries passed.
4. `ctr` had both internal `10.1.1.2` and public `1.1.1.1` DNS servers. During the outage, `systemd-resolved` selected the public server and kept using it after AdGuard recovered. The public wildcard made `smb.l3b.cc.cd` resolve to proxy `10.1.1.3` instead of Store `10.1.1.12`. The Proxmox hosts and `ctr` now use only `10.1.1.2`; `ctr`'s cloud-init setting and guest Netplan file were both aligned. A second internal DNS replica is needed for DNS redundancy; a public resolver is not equivalent for split-horizon names.
5. Store's Samba password, the Proxmox CIFS password files, and `ctr`'s credential file had drifted from the existing `Store SMB` vault item. The live passwords were reconciled to that item without exposing them. `/etc/samba` had mode `0644`, blocking Samba from traversing to its username map; it is now `0755`.

## Recovery and prevention

- Verified SSD serials, ext4 UUIDs, and `.store-volume` markers before mounting; no formatting or backup-file deletion occurred.
- Mounted AV, BACKUP, and ISO on px10. Temporarily removed CT bind definitions while CT 109 was stopped, migrated its replicated 8 GiB root disk to px10, reattached the bind definitions, and restarted through HA.
- Added `local:snippets/store-mount-guard.sh` on px10 and px20. Proxmox invokes it before CT 109 starts. It requires the exact AV/BACKUP/ISO UUIDs and markers; a missing or wrong disk aborts startup. A test passed on px10 and rejected px20 without the disks.
- Renamed the backup host/CT mount, Samba share, Proxmox storage ID, scheduled job, metrics paths, and vault URL from `PX` to `BACKUP`. The existing archives remained on the same ext4 LV. `BACKUP` and `ISO` were visible on all cluster nodes; the old `PX` storage ID, secret, and mount units were removed.
- Kept `7.0.14-17-pve` on each Proxmox host as the fallback to the running `7.0.14-19-pve`. The unused, unselected `7.0.2-6-pve` package was purged on all three after an APT simulation showed only that one package would be removed. `proxmox-boot-tool status` confirmed both bootable versions remained on each UEFI partition.

## Manual recovery after a future px10 failure

1. Stop CT 109 through HA and confirm it is stopped. Move both USB SSDs to px20. Verify both hardware serials, all three UUIDs, and filesystem markers; start the three mount units on px20. Do not start a CT against plain directories.
2. If the replicated CT root disk must be relocated, temporarily remove `mp0`, `mp1`, and `mp2` from the stopped CT config, migrate/relocate the OS disk to px20, and restore the three bind definitions against the now-mounted px20 paths. Keep the hookscript configured.
3. Start CT 109 through HA. Confirm all three mounts *inside* the CT, `smbd`, `pvesm list BACKUP`, and `pvesm list ISO` from the cluster. Confirm `ctr`'s `/mnt/AV` CIFS mount and application health.

Automatic failover of the CT's OS disk does **not** move either physical USB SSD. Without a second copy or genuinely shared storage, fully automatic service recovery is impossible; the hook intentionally fails closed until an operator moves and mounts the disks. The mount-order fix is deployed, but full reboot validation remains for the next scheduled maintenance reboot.
