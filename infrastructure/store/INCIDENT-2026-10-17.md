## Evidence and cause boundary

On px10, kernel events at 08:27–08:34 Asia/Kolkata showed an ATA passthrough timeout, UAS resets, failed writes to `sdc1`, an aborted ext4 journal, an offline SCSI device, and an emergency read-only remount. Directory reads returned I/O errors on the host and in CT 109. SMB mounts and Proxmox's storage-active indicator did not detect the underlying data-path failure.

The affected device is the CONSISTENT SSD S7 256 GB, ATA serial `20260200000000001716`, ext4 UUID `a19cf10d-4e36-4e00-94ce-bacc9381b30b`, through Realtek `0bda:9201` at USB `2-7`, interface `2-7:1.0`. This is **not** the Crucial X9 Pro serving AV/BACKUP. The evidence establishes a USB/SCSI storage-path failure and ext4 journal abort, not which physical component failed. SSD, bridge, cable, port/power and UAS behavior remain candidates.

VM 108's `scsi0` was `ISO:108/vm-108-disk-0.qcow2`, with its installer attached from ISO as well. QEMU reported 531 failed writes, 52 failed reads and six failed flushes. Guest consistency must be checked after recovery; no-loss recovery cannot yet be claimed.

All three physical Proxmox `nic0` interfaces were verified at 1000 Mb/s, full duplex, autonegotiation enabled and link up. Historical NIC errors/flaps exist, but current link negotiation does not explain the local USB/offline/ext4 errors. No NIC speed configuration was changed.

## Applied containment

1. Attempted graceful VM 108 shutdown; its guest agent timed out. Stopped the VM to end writes to the failed disk.
2. Disabled PVE storage ISO, closed Samba ISO connections and normally unmounted `/mnt/pve/ISO` on all three nodes.
3. Stopped CT 109 through HA briefly, unmounted the host ISO filesystem, and removed only its `mp2` bind definition. Restarted CT through HA with AV/BACKUP intact. Their directories and backup listings were readable, and Jellyfin remained healthy.
4. Kept the Samba ISO marker check in place, so the empty underlying directory is not exposed as a valid ISO share.
5. A USB device reset alone left SCSI offline. Unbinding/rebinding only `2-7:1.0` from the UAS driver restored the correctly identified device and partition. The Crucial device and USB controller were not reset.
6. Set both `/dev/sdc` and `/dev/sdc1` read-only using `blockdev --setro`. No filesystem repair, formatting or source deletion has been performed.
7. Installed Debian `gddrescue` 1.29-1 and started a resumable image of the entire ext4 partition on local healthy ZFS.

## Prevention applied

The pre-start guard on px10 and px20 now rejects read-only/emergency-read-only volumes and failed directory reads, in addition to checking UUID and marker. The read probe has a ten-second timeout. ISO is required whenever its expected `mp2` bind is configured; explicitly removing that optional bind permits AV/BACKUP-only service during ISO recovery. Unexpected `mp2` mappings fail closed. Both deployed script hashes matched the repository, px10's AV/BACKUP-only check passed, and px20 rejected startup with its external volumes absent.

The guard only runs at CT start. It does not prevent a later hardware failure or prove filesystem/data integrity. Independent runtime monitoring, a verified recovery copy, stable hardware and moving active guest disks off this USB share are required to reduce recurrence impact.
