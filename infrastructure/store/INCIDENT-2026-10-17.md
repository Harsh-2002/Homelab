# ISO USB storage outage, 2026-10-17

## Status: recovery in progress

The ISO share is deliberately disabled cluster-wide. ZimaOS VM 108 is stopped because its active system disk was on this share. Do not start VM 108 or mount/repair the original ISO filesystem while imaging is in progress. AV and BACKUP remain available from CT 109.

## Evidence and cause boundary

On px10, kernel events at 08:27–08:34 Asia/Kolkata showed an ATA passthrough timeout, UAS resets, failed writes to `sdc1`, an aborted ext4 journal, an offline SCSI device, and an emergency read-only remount. Directory reads returned I/O errors on the host and in CT 109. SMB mounts and Proxmox's storage-active indicator did not detect the underlying data-path failure.

The affected device is the CONSISTENT SSD S7 256 GB, ATA serial `20260200000000001716`, ext4 UUID `a19cf10d-4e36-4e00-94ce-bacc9381b30b`, through Realtek `0bda:9201` at USB `2-7`, interface `2-7:1.0`. This is **not** the Crucial X9 Pro serving AV/BACKUP. The evidence establishes a USB/SCSI storage-path failure and ext4 journal abort, not which physical component failed. SSD, bridge, cable, port/power and UAS behavior remain candidates.

VM 108's `scsi0` was `ISO:108/vm-108-disk-0.qcow2`, with its installer attached from ISO as well. QEMU reported 531 failed writes, 52 failed reads and six failed flushes. Guest consistency must be checked after recovery; no-loss recovery cannot yet be claimed.

All three physical Proxmox `nic0` interfaces were verified at 1000 Mb/s, full duplex, autonegotiation enabled and link up. Historical NIC errors/flaps exist, but current link negotiation does not explain the local USB/offline/ext4 errors. No NIC speed configuration was changed.

## Applied containment

1. Attempted graceful VM 108 shutdown; its guest agent timed out. Stopped the VM to end writes to the failed disk.
2. Disabled PVE storage ISO, closed Samba ISO connections and normally unmounted `/mnt/pve/ISO` on all three nodes.
3. Stopped CT 109 through HA briefly, unmounted the host ISO filesystem, and removed only its `mp2` bind definition. Restarted CT through HA with AV/BACKUP intact. Their directories and backup listings were readable, and Jellyfin remained healthy.
4. Kept the Samba ISO marker check in place, so the empty underlying directory is not exposed as a valid ISO share.
5. A USB device reset alone left SCSI offline. Unbinding/rebinding only `2-7:1.0` from the UAS driver restored the correctly identified device and partition. The Crucial device and USB controller were not reset.
6. Set both `/dev/sdc` and `/dev/sdc1` read-only using `blockdev --setro`. No filesystem repair, formatting or source deletion has been performed.
7. Installed Debian `gddrescue` 1.29-1 and started a resumable image of the entire ext4 partition on local healthy ZFS.

## Recovery artifacts and continuation

- Dataset: `data/iso-recovery-20261017`, mount `/data/iso-recovery-20261017` on px10, compression lz4, recordsize 1 MiB.
- Source: `/dev/disk/by-uuid/a19cf10d-4e36-4e00-94ce-bacc9381b30b`, 256,059,448,832 bytes. Revalidate UUID/serial before any device operation.
- Image: `iso-partition.img`; resumable map: `iso-partition.map`.
- Directory mode 0700; image/map/logs mode 0600. The image contains private guest data and must not be uploaded to Git, Notion or memory.
- Initial buffered pass was stopped cleanly after about 12.46 GB to switch to direct reads. No read errors had been recorded at that checkpoint. This does not establish full-disk integrity.
- The direct-read unit `iso-rescue-20261017-direct.service` subsequently failed: the disk went offline again, with about 15.76 GB (6.16%) rescued. It recorded 216,395 failed read operations after the transport failure. These are not proof of that many physically bad sectors; the map still needs a successful device read pass.
- After the owner was asked to reconnect the ISO SSD, a fresh check found the correct serial/UUID running and unmounted. Kernel logs recorded USB disconnect/re-enumeration at 23:57:41–42 IST on October 17, still on USB port `2-7`; a cable/port change is not established by this evidence.
- At 01:26 IST on October 18, source disk/partition write protection was reapplied (USB re-enumeration clears it) and imaging resumed as `iso-rescue-20261018-reconnect.service`. The same image/map are used with direct reads, 1 MiB blocks, `--try-again` to requeue transport-failed ranges, input-size verification, `--check-on-error`, a maximum of eight read errors, and a 30-second no-success timeout. The additional checks stop another offline device from generating a prolonged sweep of failed reads. Re-detection alone does not establish stable hardware or completed recovery.
- Logs: `ddrescue.log`, `ddrescue-direct.log` and `ddrescue-reconnect.log` in the recovery directory. Use `systemctl status`, `journalctl -k`, `ddrescuelog -t iso-partition.map` and the log to inspect progress. Do not run another copier against these output files concurrently.
- The reconnect run exited normally after its resumed fifth pass, but the map still showed 226.80 GB non-tried and only 29.26 GB rescued (11.43%). A normal process exit or `Finished` message is **not** proof of a complete recovery. A new run, `iso-rescue-20261018-pass1.service`, explicitly selects copying pass 1 with `--cpass=1 --min-read-rate=0` against the same source/image/map, retaining the input-size/error-stop checks. Its log is `ddrescue-pass1.log`. Initial verified progress passed 30.14 GB with zero new read errors; the untried remainder must still be read. ISO remains disabled and VM 108 stopped.
- At 01:29:51 IST October 18, the disk went offline again during this read-only first pass. Kernel reports `Device offlined - not ready after error recovery`, UAS recovery and failed READ commands around sector 32509952. The copier stopped with `Input file no longer returns data: Input/output error`, preserving about 30.14 GB. Recovery is now **stopped**, not running. Physical SSD failure is still unproven; USB transport/adapter/cable/port and media/controller failure must be distinguished. Do not simply re-enable ISO or keep blindly resetting the device.
- The owner then changed the physical USB port. Logs confirm removal from `2-7` at 01:35:51 IST and enumeration on `2-8` at 01:36:21–22 IST, with the same SSD serial, UUID and partition size. At the next check the device was running and unmounted. Write protection was reapplied and imaging resumed as `iso-rescue-20261018-port8.service`, logging to `ddrescue-port8.log`, with the same protected image/map. This run explicitly selects pass 1, requeues the prior transport-failed block and retains input-size/error-stop checks. Sustained-read validation and full image verification remain required; changing ports alone does not establish the root cause or fix.
- The first 35-second sample on port `2-8` passed the prior failing read region and reached 31.25 GB rescued (12.20%) with zero new read errors and device state running. This is encouraging but is not a completed disk recovery or proof that the old port was the only fault.
- The port-8 run subsequently failed at 46.61 GB rescued (18.20%). On the owner's explicit request, another verified/unmounted/write-protected-source attempt was started at 02:07 IST as `iso-rescue-20261018-retry0207.service`, using the same image/map and error-stop checks. It failed after 23 seconds with `Input file no longer returns data: No such device (errno=19)`, after preserving 46.64 GB (18.21%). Kernel logs showed USB re-enumeration; the device was detected again by the follow-up check, but the copier was stopped. A powered enclosure/LED and a `running` state after re-enumeration do not establish stable I/O. Do not present this recovery as still running or complete. Source partition write protection was reapplied after re-enumeration.

Remaining work, **not yet completed**:

1. Finish imaging and assess all unread/unrecoverable map ranges. If the device repeatedly disconnects, stop and arrange a cable/bridge/port check instead of blind retries.
2. Snapshot the recovery dataset before repairing its working image. Assess with offline `e2fsck -fn`; repair the copy only after reviewing results. Never repair a mounted filesystem or the only preserved failing source.
3. Mount the recovered image read-only, inventory files and validate the ZimaOS QCOW2 offline with `qemu-img check`.
4. Recover/import VM 108's system disk into PX30 local ZFS, validate equivalence and boot/application health. Keep the original recoverable until validation is complete. Do not operate the VM from the USB SMB disk again.
5. Establish stable source hardware before restoring ISO. Reattach CT bind `mp2: /mnt/external/ISO,mp=/srv/ISO,replicate=0` during a controlled CT restart, validate the guard and share, then re-enable cluster storage. Test real file reads and a disposable write from all three nodes.
6. Distinguish ISO/template storage and disk-image import staging from **active VM disks**. Installed CIFS backend supports `import` content; `images` permits live VM disks and is not merely an upload/import setting. Do not remove existing content or disks before checking references.

## Prevention applied

The pre-start guard on px10 and px20 now rejects read-only/emergency-read-only volumes and failed directory reads, in addition to checking UUID and marker. The read probe has a ten-second timeout. ISO is required whenever its expected `mp2` bind is configured; explicitly removing that optional bind permits AV/BACKUP-only service during ISO recovery. Unexpected `mp2` mappings fail closed. Both deployed script hashes matched the repository, px10's AV/BACKUP-only check passed, and px20 rejected startup with its external volumes absent.

The guard only runs at CT start. It does not prevent a later hardware failure or prove filesystem/data integrity. Independent runtime monitoring, a verified recovery copy, stable hardware and moving active guest disks off this USB share are required to reduce recurrence impact.
